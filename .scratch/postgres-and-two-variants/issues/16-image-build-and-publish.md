# 16 - Image build and bundle publish pipeline

Status: ready-for-human

**What to build:** A push produces the container image and publishes the frontend bundle, so the demo
tracks the branch without the Operator running commands by hand. One pipeline produces the single
image both Variants run, which is what makes "works on the homelab" imply "works in the demo"
(ADR-0002).

The spec left this an open item to settle during planning. It is settled here.

**The registry is GitHub Container Registry, public.** ECR would mean a long-lived AWS credential
sitting permanently on the homelab, which is what the developer site's ADR-0002 went out of its way
to avoid and what [ADR-0010](../../../docs/adr/0010-demo-guardrails-on-shared-hardware.md) leans on
when it argues a foothold on the homelab does not become a foothold in the AWS account. A public
image needs no credential at all. It holds no secrets: every password arrives from `.env` when the
container starts, and the source is already public.

Publishing needs only `permissions: packages: write` and the run's own `GITHUB_TOKEN`. Nothing is
stored and nothing is rotated. Two tags per build: the commit SHA, which is what `.env` pins on the
homelab, and a moving `main` so the current build is visible without being the thing that runs.

**One manual step to record in the runbook.** A package pushed from a repository starts private. The
visibility is flipped once in GitHub's package settings and stays flipped. It is exactly the sort of
one-time step that is forgotten and then presents months later as an inexplicable pull failure.

**Human-only.** The Operator is writing this workflow. Not to be dispatched to an agent.

**Blocked by:** 15, for the object storage and the deploy role the bundle half publishes to. The
image half is not blocked and can go first.

- [ ] A push builds the container image and publishes it to GHCR where both Variants can pull it
- [ ] The package is public, and the homelab pulls with no stored credential
- [ ] The same commit produces the bundle published to the demo's object storage
- [ ] The image carries a tag traceable back to its commit, and `.env` on the homelab pins the SHA
- [ ] Migrations run against the demo database as part of a deploy, or through a documented step
- [ ] Tests run in the pipeline against a real Postgres, and a failure blocks publish
- [ ] The recorded Seed from ticket 21 is regenerated by the build rather than committed stale
- [ ] No credential appears in the repository or in pipeline logs
- [ ] The one-time package-visibility step is written into the runbook
