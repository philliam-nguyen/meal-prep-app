# 16 - Image build and bundle publish pipeline

Status: ready-for-human

**What to build:** A push produces the container image and publishes the frontend bundle, so the demo
tracks the branch without the Operator running commands by hand. One pipeline produces the single
image both Variants run, which is what makes "works on the homelab" imply "works in the demo"
(ADR-0002).

The spec left this an open item to settle during planning. It is settled here.

**The registry is GitHub Container Registry, public.** ECR would mean a long-lived AWS credential
sitting permanently on the homelab, which is what the developer site's ADR-0002 went out of its way
to avoid and what [ADR-0010](../../../docs/adr/0010-demo-guardrails-on-shared-hardware.md) leans on
when it argues a foothold on the homelab does not become a foothold in the AWS account. A public
image needs no credential at all. It holds no secrets: every password arrives from `.env` when the
container starts, and the source is already public.

Publishing needs only `permissions: packages: write` and the run's own `GITHUB_TOKEN`. Nothing is
stored and nothing is rotated. Two tags per build: the commit SHA, which is what `.env` pins on the
homelab, and a moving `main` so the current build is visible without being the thing that runs.

**One manual step to record in the runbook.** A package pushed from a repository starts private. The
visibility is flipped once in GitHub's package settings and stays flipped. It is exactly the sort of
one-time step that is forgotten and then presents months later as an inexplicable pull failure.

**Human-only.** The Operator is writing this workflow. Not to be dispatched to an agent.

**Blocked by:** 15, for the object storage and the deploy role the bundle half publishes to. The
image half is not blocked and can go first.

- [x] A push builds the container image and publishes it to GHCR where both Variants can pull it
      (2026-08-20: `ci.yml` `publish-image` green, two tags pushed)
- [x] The package is public, and the homelab pulls with no stored credential (2026-08-20: proven on
      the homelab with `docker logout ghcr.io` then a successful pull)
- [ ] The same commit produces the bundle published to the demo's object storage (`publish-bundle`
      is written and main-gated; the deploy role's trust policy only accepts `refs/heads/main`, so
      the first merge to main is its verification)
- [x] The image carries a tag traceable back to its commit (the SHA tag), and `.env` on the homelab
      pins the SHA (the runbook's image bullet now says pin the SHA, never `main`; the homelab's

- [x] Migrations run against the demo database as part of a deploy, or through a documented step
      (documented: `docker compose up -d` reruns the migrate service, per the runbook's Upgrading
      section; a deploy is bump the SHA in `.env`, pull, up)
- [x] Tests run in the pipeline against a real Postgres, and a failure blocks publish (2026-08-20:
      testcontainers Postgres in the `test` job; a real failure, the backup readiness race, blocked
      both publish jobs via `needs: test`)
- [x] The recorded Seed from ticket 21 is regenerated by the build rather than committed stale
      (`npm run record` runs before `docker build` in `publish-image`; `npm run build` in
      `publish-bundle` records first by definition)
- [x] No credential appears in the repository or in pipeline logs (no repository secrets exist: GHCR
      uses the run's ephemeral `GITHUB_TOKEN`, AWS uses OIDC via `id-token: write`; bucket,
      distribution and role ARN are repository variables because they are not secrets)
- [x] The one-time package-visibility step is written into the runbook (inverted from the ticket's
      prediction: the package inherited public from the public repository, so the runbook note warns
      the visibility silently follows the repository rather than asking for a flip)

## Comments

**2026-08-20: built as `.github/workflows/ci.yml`, one workflow, three jobs.** `test` runs the full
suite on every push to any branch; `publish-image` and `publish-bundle` both carry
`needs: test` and `if: github.ref == 'refs/heads/main'`, so a red suite or a feature branch
publishes nothing. Verified on `postgres-migration`: test green, both publish jobs skipped. The one
open box closes on the first merge to `main`, which is also when the bundle half runs for the first
time. One incidental fix along the way: the backup suite's readiness probe raced the Postgres
image's init-phase restart in CI (`pg_isready` over the unix socket answers ready during init);
the probe now forces TCP with `-h 127.0.0.1`, which only the final server listens on.
